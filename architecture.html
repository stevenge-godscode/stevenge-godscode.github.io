01 · 技术栈位置

把业务 Glue 从每个 AI 应用里抽出来

企业 AI 的重复问题通常不是缺 Data Platform、RAG、模型或 Agent，而是业务含义、当前事实、规则、证据、权限和工作方法长期散落在每个应用自己的 Prompt、SQL、检索逻辑、Workflow 和 Tool Mapping 里。

应用内局部业务逻辑

每个应用都独立重建一次相同的企业上下文。

AI 应用 APrompt + RAG + 本地规则 + SQL + Tool Mapping
AI 应用 BPrompt + 检索 + 重复语义 + Workflow 条件
Agent CSystem Prompt + 自定义 Adapter + 应用内权限规则

企业共享业务能力

应用共享同一个受治理的业务世界，而不是每增加一个应用就重新“教一遍公司”。

业务上下文与能力平面业务对象 · 事实 · 证据 · 规则 · 方法 · 权限 · 任务上下文 · 业务能力
应用 A调用受治理业务能力
应用 B复用相同语义与证据合同
Agent C调用企业共享能力，而不是自己维护业务逻辑
02 · 系统架构

当前工程刻意把数据生产、语义运行、领域资产、业务应用和跨项目发布治理分开。每个独立部署的软件系统拥有自己的运行数据库、代码责任和发布责任。

04 · 运行链路

一个业务能力被调用时 系统到底发生什么

能力不能因为“元数据里声明了”就算真实存在。它必须能够解析精确数据和语义绑定，调用真实 Data Product / Provider，通过证据、失败和降级门禁，并返回可追溯结果。

01
能力请求

业务应用或 Agent 使用 Workspace Client 和已授权身份调用通用 Capability。

02
Workspace 解析

解析精确 Core、Domain Pack、Mapping、数据合同、权限和发布状态。

03
数据需求解析

把领域逻辑数据需求翻译成精确的 Data Product 操作和参数。

04
受治理执行

通过 Deployment 管理的服务身份调用 Data Product 或确定性 Provider。

05
语义投影

校验 Schema、身份、类型、时间、单位、来源和领域映射。

06
证据门禁

判断完整性、新鲜度、冲突状态、失败语义和是否具备可回答条件。

07
判断与方法

执行确定性策略，并在允许范围内让模型基于受治理上下文完成受限推理。

08
结果与追踪

返回事实、证据、限制、方法版本、允许动作和完整审计追踪。

一项能力只有经过六个不同状态后才允许公开发布：
  1. Domain Pack 声明数据需求。
  2. Data Product Contract 能真实提供该需求。
  3. Mapping Set 与精确 Workspace Binding 已发布。
  4. Runtime Adapter 或 Provider 能实际执行。
  5. Evidence、Failure 与 Degradation 行为通过端到端验证。
  6. 最后才进入通用 Capability Directory 对外发布。
05 · 可信与治理

可信来自受控业务链 而不是“相信模型”

Genesis 将来源治理、上下文授权、确定性策略、模型判断、动作边界和审计分开管理。证据缺失或冲突是一种正常治理状态，模型不能用流畅表达把它掩盖掉。

受治理来源权威级别、来源、采集状态
可追溯事实时间、版本、质量、冲突状态
授权上下文用户、目的、范围、能力边界
受控判断规则、方法、证据、受限推理
有边界行动建议、审批、执行或禁止
可审计结果Decision Trace、人工覆盖和业务结果

确定性策略

Hard Rule、阈值、权限和不可逆动作约束不能交给自由形式的模型推理。

模型判断

模型可以解释非结构化证据，并在已声明规则、权限、证据和 Capability 合同范围内完成推理。

证据缺失、过期、冲突或无权限 → 显式返回数据缺口、部分结果、升级人工或停止条件。表达得再漂亮也不能替代缺失证据。

07 · 发布与部署

代码 数据 语义制品和运行绑定分别发布

当前 Deployment Contract 只重建真正拥有可执行行为变化的组件。数据刷新、Ontology 变化、Domain Pack 和 Mapping 变化不会触发无关镜像重建。

平台 / 应用代码拥有变更的可执行组件 → 不可变镜像 Digest
受治理数据Pipeline Run → 不可变 Snapshot / Serving Version
Core / Domain Pack不可变语义制品 → 精确版本 + SHA-256 身份
Mapping / Binding版本化集成制品 + 受治理运行配置
GitHub CI精确 Commit · 各仓自身 Gate · 不可变构建证据
→
DEV 验收日常开发可用 Source Mode；正式验收使用 Digest 固定的 Immutable Candidate
→
STAGING 晋级直接晋级已经通过 DEV 验收的同一 Candidate，不重新构建、不改变组件 Digest
当前 Deployment Owner：genesis-deployment 统一负责跨项目环境装配、Release Lock、晋级证据和回滚合同。STAGING 必须使用不可变制品；DEV 可以使用受保护 Source Overlay，但 Source Mode 永远不能直接晋级。

09 · 当前工程实现
