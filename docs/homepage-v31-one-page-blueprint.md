# Genesis V31：首页单页结构与视觉规范

> 目标：把此前 N00–N12、Closed-loop Scenario Framework、Proof Framework 以及已形成的视觉原则，收敛成一个业务用户和技术负责人都能快速看懂的**单页首页**。不再用“产品模块目录”组织页面，而用客户认知顺序组织页面。

---

# 1. 首页只讲一件事

> **Genesis 让现有通用 AI 真正进入企业业务：理解真实业务、按企业方式判断，并在边界内采取行动，改变真实业务状态。**

首页不负责讲完 Ontology、GraphRAG、Evidence、Domain Pack、Capability API 等全部技术概念；这些概念只在需要解释“为什么成立”时出现。

首页的认知路径固定为五段：

```text
一句话 + 一个图：Genesis 是什么
        ↓
痛点：为什么通用 AI 到企业里不好用
        ↓
目标：企业真正想要什么样的 AI
        ↓
Gap：Genesis 到底填补哪一层
        ↓
怎么做：用一个真实闭环场景讲完整
```

这是整个单页结构。其他内容只能嵌入这五段，不再额外生长成独立大章节。

---

# 2. Section 1 — 一句话 + 一个图描述 Genesis

## 一句话

主标题继续保留：

> **让 AI 真正为你的公司工作**

一句产品解释首选：

> **Genesis 把企业的业务世界交给通用 AI，让它理解事实、按你的规则判断，并通过受控行动改变真实业务状态。**

这句话必须同时让两类人听懂：

- 业务负责人：AI 不只是回答，而是真的进入工作；
- 技术负责人：Genesis 不替换 LLM / Data / Agent，而是连接业务世界、判断与行动。

## 一个图

Hero 图只表达一个完整闭环，不再用三张产品卡：

```text
企业业务世界
系统 · 数据 · 文档 · 规则 · 方法
       ↓
     Genesis
Business Context & Capability
       ↓
   通用 AI / LLM
理解 · 推理 · 判断
       ↓
受控 Action
Agent · Workflow · API · Human Approval
       ↓
真实业务状态改变
       ↓
新的 Facts / Evidence
       ↺ 回到 Genesis
```

图中 Genesis 是**共享 Business Context & Capability Plane**，不是所有数据必须经过的 ETL 中间件，也不是 Agent Platform。

### Hero 图必须同时表达三件事

1. **继续使用现有模型**：GPT / Claude / DeepSeek / Qwen 等只是能力来源；
2. **继续使用现有系统**：ERP / CRM / DB / Data Platform 是 Source of Truth；
3. **行动改变真实世界**：判断通过受控 Action 改变业务状态，新状态再变成新 Facts。

# 3. Section 2 — 痛点：为什么通用 AI 到企业里不好用

标题：

> **通用 AI 很聪明，但一到你的公司就不好用了。**

不要罗列十几个技术问题。只说四个业务用户能立即认出的症状：

## 01 不知道现在发生了什么

通用模型不知道企业当前真实状态：客户、合同、项目、设备、订单、市场、学生等当前发生了什么。

对应：**Facts**。

## 02 不知道这些信息在你公司意味着什么

拿到字段、文档和数据，不等于理解业务对象、关系、状态和上下文。

对应：**Business Semantics & Context**。

## 03 不知道你们公司是怎么判断的

同样的数据，不同企业会按不同指标、规则、方法、策略和风险边界判断。

对应：**Rules / Methods / Domain Pack**。

## 04 即使给出答案，也不等于能工作

企业真正需要的是：判断之后能安全地创建任务、发起流程、调用 API、更新系统，并知道什么必须由人确认。

对应：**Capability / Action / Boundary**。

核心结论：

> **问题不是模型不够聪明，而是它没有真正进入你的业务世界。**

---

# 4. Section 3 — 目标：企业真正需要的不是“更会聊天的 AI”

标题：

> **企业需要的，是一个真正能参与工作的 AI。**

目标不写成“企业专属大模型”，而写成四种工作能力：

## 懂公司

知道你的业务对象、关系、事实和上下文。

## 会判断

按企业自己的规则、方法和 Evidence 形成结论，而不是临时猜。

## 能行动

在权限和风险边界内调用现有 Agent / Workflow / API 改变业务状态。

## 知道边界

证据不足、冲突、越权或高风险时停止，明确说不知道或交给人。

一句目标描述：

> **从“回答问题”到“理解业务、形成判断、采取行动、完成工作”。**

这个 Section 是业务价值目标，不讲架构。

---

# 5. Section 4 — Genesis 填补 Gap

标题：

> **你已经有数据，也有 AI。Genesis 填补中间缺失的业务理解与能力。**

不要把 Genesis 说成“比 Data Platform / RAG / Agent 更高级”，而是职责分工：

```text
Data Platform
让数据可治理、可计算、可访问

        ↓ / 可复用

Genesis
把企业事实、语义、规则、上下文和业务能力
组织成 AI 可持续使用的 Business Context & Capability

        ↓ / 可复用

LLM / AI
理解、推理、生成、判断

        ↓

Agent / Workflow / App
执行受控动作
```

一句人话：

> **数据平台把数据准备好；Genesis 把业务讲明白并定义怎么工作；大模型负责思考；Agent 和流程负责执行。**

## 技术负责人下钻时只解释四个核心资产

### Business Model

什么是什么、彼此什么关系。

### Facts & Evidence

现在什么是真的、来自哪里、是否仍有效。

### Context & Rules

当前任务需要知道什么，以及企业怎么判断。

### Business Capability

这类工作怎样稳定重复完成：输入、输出、规则、Evidence、权限、Action、人工确认条件。

这里自然出现 Domain Pack：

> **Domain Pack = 专业领域共性 + 企业自己的工作方式。**

不单独再做 Domain Pack 大章节。

# 6. Section 5 — 怎么做：一个真实闭环场景讲完整

首页不再把“理解”和“Action”拆成两个概念区，而用一个真实 instance 从头走到底。

主场景首选：**客户经营风险 / 重点关注**。

用户问题：

> **“这个客户现在有风险吗？”**

## S1 Observe — 看见真实世界

具体 instance：

- 客户：南桥集团；
- 合同：HT-2026-0188，800 万；
- 应收：逾期 18 天；
- 项目：交付中、尚未验收；
- 客户等级：战略客户。

来源：ERP / CRM / 项目系统 / 合同。

回答：**现在发生了什么？**

## S2 Understand — 看懂业务世界

Genesis 识别：

- 客户 ↔ 合同 ↔ 项目 ↔ 应收之间的关系；
- 付款条件与验收相关；
- 当前任务不是简单“看逾期天数”，而是判断客户是否存在风险。

回答：**这些事实意味着什么？**

## S3 Decide — 按企业方式判断

企业规则：

- 战略客户逾期超过 15 天进入重点关注；
- 项目未完成验收时，不直接认定信用风险；
- 正式信用等级调整必须人工确认。

Genesis 输出：

> **建议列入重点关注，但当前证据不足以认定信用风险。应先确认交付与验收责任。**

回答：**应该怎么判断？依据是什么？**

## S4 Act — 采取受控行动

允许自动 / 半自动执行：

- 创建客户重点跟进任务；
- 指派客户经理；
- 请求项目负责人补充验收状态；
- 拉取合同付款条件；
- 发起风险复核流程。

禁止自动执行：

- 直接修改正式信用等级；
- 自动发违约通知。

回答：**AI 现在可以做什么？什么必须人确认？**

## S5 Verify — 验证行动是否改变了业务

后续读取：

- 跟进任务是否完成；
- 验收状态是否更新；
- 风险复核是否确认；
- 应收状态是否变化；
- 采取行动后结果是否符合目标。

回答：**行动有没有真正解决问题？**

## S6 Learn / Institutionalize — 沉淀

沉淀：

- Decision Trace；
- 人工确认 / 覆盖；
- Action Outcome；
- Rule / Method 调整建议；
- 可复用 `CustomerRiskAssessment(customer_id)` Capability。

回答：**这次工作如何让下一次更好、更快、更一致？**

完整闭环：

```text
Observe → Understand → Decide → Act → Verify → Learn
   ↑                                      ↓
   └──────────── New Facts ──────────────┘
```

## 横向 Trust 约束

Trust 不是第七阶段，而是贯穿 S1–S6：

> **有依据 / 有权限 / 有边界 / 知道什么时候不知道 / 可追溯 / 可人工接管**

# 7. 多场景证明“不是只适用于经营”

首页主场景只完整展开一个，下面用一条紧凑横向矩阵证明跨场景成立，不再做四张大行业卡。

| 场景 | Observe | Understand | Decide | Act | Verify / Learn |
|---|---|---|---|---|---|
| 经营 | 应收 / 项目状态 | 客户-合同-项目关系 | 风险规则 | 跟进 / 复核 | 回款 / 验收 / Trace |
| 运维 | Metrics / Trace | 服务拓扑 / 变更 | P1 / 根因 | 扩容 / 工单 / 审批 | 指标恢复 / Incident |
| 投研 | 行情 / 新闻 / 持仓 | 标的-板块-策略 Context | 策略规则 | Watchlist / 报告 / 审批后交易 | 后续表现 / 策略复盘 |
| 教育 | 测验 / 作业 | 知识点依赖 | 教学规则 | 学习任务 / 教师确认 | 新测验 / 掌握度 / 教师反馈 |

注意：矩阵表达**设计闭环**，真实验证状态必须由 `Proof Level + Asset Status + Loop Coverage` 单独标记，不能因为设计完整就说已经生产可用。

---

# 8. Proof / 场景成熟度如何进入单页

首页不再单独占一大屏展示 Early Results。

在“怎么做”的主场景之后，用一条简短 Proof Strip：

- 已实现原型；
- Working Demo；
- Customer POC；
- Production。

若某场景有真实 P2/P3，则优先展示该场景；当前没有对应 Proof 时，只标“场景设计 / 已实现原型”，不做客户成功暗示。

Living Registry：`docs/scenario-proof-registry.md`。

# 9. 页面结尾

不增加第六个产品章节，只做收束：

> **不是让 AI 回答更多，而是让更多工作真正可以交给 AI。**

三项结果：

- 判断更可靠；
- 行动有边界；
- 能力持续沉淀和复用。

CTA：

> **拿一个真实业务问题来验证 ›**

辅助：

> 不需要先治理整个公司，也不需要先建立巨大 Ontology。从一件最希望 AI 做好的工作开始。

# 10. 视觉风格固定规范

## 总体气质

- 企业级、克制、专业，不做消费级“AI 科技感”；
- Apple-like 的留白与排版秩序，但不模仿 Apple 产品页；
- 不做典型 SaaS icon wall、彩色功能卡墙、机器人插画、咨询 PPT 流程图；
- 图形优先使用真实数据、文字、关系、状态变化；
- 页面需要让业务用户先看懂，技术负责人继续读不会觉得虚。

## 颜色

只使用：

- 白 / 浅灰；
- 深黑 / 深灰；
- Genesis 蓝作为唯一主强调色。

不使用绿色“success”作为主视觉语义，不用多彩渐变堆科技感。

## 圆角

- 大画布：14–18px；
- 内部控件 / 状态块：6–10px；
- 避免 20–24px 以上大圆角；
- 不到处使用胶囊按钮 / pill。

## 品牌

- Genesis Logo 必须使用真实 `src/assets/images/logo_256.png`；
- 不重绘、不 AI 生成近似 Logo；
- Logo 图形与 Genesis 字标视觉高度相等；
- 顶栏约 22px logo + 18px 字标。

## 字体与换行

- 继续使用系统字体 / SF Pro / PingFang SC 栈；
- 主标题大而克制，正文正常段落；
- 桌面端短标题避免断开；
- 移动端自然换行，但避免 2–3 个汉字形成孤行；
- 不人工堆大量 `<br>` 造成僵硬断句。

## 动效

- Hero 最多保留一条整体左 → 右缓慢刷新 / scan，周期约 9–12 秒；
- 闭环图可做非常轻的状态推进，但不使用跑点、弹跳、持续 pulse；
- 其他区块只使用轻微 reveal；
- 动效用于表达“状态变化 / 闭环”，不是装饰。

## 页面密度

- 一个 Section 只解决一个客户问题；
- 不重复同一信息；
- 不同时出现大量 4-card / 6-card / 8-card 结构；
- 首页最多一个完整主场景 + 一个跨场景矩阵；
- 技术组件清单不进入首页主体。

- [ ] “怎么做”用同一个真实 instance 贯穿 S1–S6；
