# Genesis 产品概念的场景化实例

> 目的：所有抽象定义都必须能落到真实业务 instance。Ontology、Fact、Context、Rule、Evidence、Capability 等概念，不能只靠定义解释，而要通过完整业务事件链让业务负责人和技术负责人看到“在我的场景里它到底是什么”。

## 表达原则

1. **先说人话定义，再给真实 instance。**
2. **同一套定义至少跨多个领域验证。** 如果只在一个场景成立，说明定义还不够稳定。
3. **不要把概念画成一条机械流水线。** Rule、Evidence、Permission、Capability 在真实系统中存在交叉关系。
4. **区分长期沉淀与运行时动态生成。** 这是理解 Genesis 与 Prompt / RAG / 数据搬运差异的关键。

---

# 一、统一概念边界

## 1. Business Model / Ontology：业务世界的结构

回答：

> **什么是什么？彼此什么关系？**

包括业务对象、关系、字段含义、状态含义、指标语义等。

它是相对长期、可治理、可版本化的企业业务定义。

## 2. Fact：当前真实发生的事情

回答：

> **现在什么是真的？**

Fact 来自 ERP、CRM、数据库、文档、事件、行情、监控等真实来源，并带有时间、来源、状态和证据。

重要：**Fact 不等于 Genesis 必须复制并保存所有企业数据。** Genesis 可以通过映射、查询、物化、缓存或引用等方式，让事实在统一业务语义下可访问。

## 3. Rule / Method / Boundary：企业自己的工作方式

回答：

> **遇到这种情况，这家公司怎么判断、怎么做、什么不能做？**

包括规则、指标、方法、流程、阈值、权限、审批和边界。

## 4. Context：某一次任务现在需要知道什么

回答：

> **为了完成当前任务，AI 此刻需要哪些对象、事实、关系、历史、规则和约束？**

Context 不是一个长期保存的“超级大上下文”，而是 Genesis 针对具体任务动态组装出来的 **Task Context / Business Context**。

例如“判断客户 A 是否有风险”与“给客户 A 生成续约建议”，即使面对同一客户，需要的 Context 也不同。

## 5. Evidence：为什么可以相信

回答：

> **这个事实、判断或动作依据什么？**

Evidence 不是线性链条中的一个普通步骤，而是贯穿 Fact、Context、Judgment 和 Action 的可信机制，包括数据来源、文档出处、规则版本、时间窗口和推理依据。

## 6. Capability：企业可重复使用的业务能力

回答：

> **这家公司如何稳定、重复地完成某类判断或工作？**

Capability 不是单纯 Prompt，也不是普通 API。它是一个可复用的业务能力契约，通常包含：

- 输入 / 输出；
- 需要哪些业务对象与语义；
- 需要哪些事实和 Context；
- 适用哪些规则、方法和边界；
- Evidence 要求；
- 权限要求；
- 可调用哪些工具 / Action；
- 哪些情况必须停止或交给人。

例如：

`CustomerRiskAssessment(customer_id)`

可以被 AI、Agent、App 或业务流程重复调用。

Capability 可以是：

- **理解型能力**：解释某个业务状态；
- **判断型能力**：风险评估、趋势判断、学习诊断；
- **行动型能力**：在满足权限和规则的前提下执行扩容、创建任务、更新状态等动作。

# 二、长期沉淀、动态生成与混合状态

| 内容 | 典型状态 | 说明 |
|---|---|---|
| Business Model / Ontology | 长期沉淀 | 对象、关系、语义、状态定义，持续演进并版本化 |
| 数据源映射 / Source Binding | 长期沉淀 | 企业系统字段如何映射到业务对象和事实 |
| Rule / Method / Boundary | 长期沉淀 | 企业判断方式、流程、权限、阈值、边界，可版本化 |
| Capability Definition | 长期沉淀 | 能力契约、输入输出、上下文要求、规则、工具、权限 |
| Fact | 混合 | 源数据持续变化，可实时查询、物化、缓存或引用 |
| Evidence Set | 运行时为主 | 针对本次事实、判断和动作组织实际证据 |
| Task Context | 动态生成 | 根据用户、任务、对象、当前事实、规则与权限临时组装 |
| Capability Invocation | 动态执行 | 具体一次能力调用，在当前 Context 下产生判断或行动 |

因此 Genesis 不是“把所有东西都存下来”，而是：

> **长期沉淀企业稳定的业务定义和工作方式；在运行时连接当前事实，动态形成任务上下文，并调用可复用业务能力。**

# 三、真实运行结构

不是：

```text
Ontology → Fact → Context → Rule → Evidence → Capability
```

更准确的是：

```text
       企业业务底座（长期沉淀）
┌─────────────────────────────┐
│ Business Model / Ontology   │
│ Source Binding              │
│ Rules / Methods / Boundary  │
│ Capability Definitions      │
└─────────────────────────────┘
               │
               │ 当前任务 / 当前用户
               ↓
      解析业务对象与任务意图
               ↓
      获取当前事实 + Evidence
               ↓
        动态组装 Task Context
               ↓
       选择 / 调用 Capability
               ↓
       AI 判断 / Agent 执行
               ↓
   结果 + Evidence + 可选业务回写
```

其中权限、Evidence 和边界是横向约束，而不是只在某一步才出现。

# 四、场景一：企业经营 — 哪些客户需要重点关注？

## 用户问题

> 哪些客户最近需要重点关注？为什么？

## Business Model / Ontology instance

- 客户：`南桥集团`
- 合同：`HT-2026-0188`
- 项目：`智能供应链一期`
- 应收：`AR-2026-0912`
- 客户经理：`张经理`

关系：

```text
南桥集团
  ├─签署→ HT-2026-0188
  ├─对应→ 智能供应链一期
  └─产生→ AR-2026-0912
```

## Facts

- 合同金额：800 万；
- 应收逾期：18 天；
- 项目状态：交付中、尚未验收；
- 南桥集团为战略客户；
- 上季度曾发生一次 12 天延期回款。

## Rules / Methods / Boundaries

- 战略客户应收超过 15 天进入重点关注；
- 项目尚未验收时，不直接认定为信用风险；
- 必须先检查交付与验收责任；
- 风险升级必须由业务负责人确认。

## Task Context

针对“是否重点关注”动态组合：

- 客户等级；
- 当前合同；
- 当前应收；
- 项目交付 / 验收状态；
- 历史回款行为；
- 当前责任人；
- 当前适用规则；
- 用户权限。

不是把整个 ERP / CRM 全部交给模型。

## Evidence

- ERP 应收记录；
- CRM 客户等级；
- 项目系统状态；
- 合同条款；
- 历史回款记录；
- 当前规则版本。

## Capability

`CustomerRiskAssessment(customer_id)`

输出：

> 南桥集团建议进入重点关注，但当前证据不足以认定为信用风险。主要原因是应收已逾期 18 天，但项目尚未完成验收。建议先确认交付与验收责任，再由业务负责人决定是否升级风险等级。

这里的关键不是“AI 会写这段话”，而是同一套客户风险能力可以被经营驾驶舱、AI 助手、Agent 和流程共同调用。

# 五、场景二：智能运维 — 一个告警到底严重不严重？

## 用户问题

> 支付服务 CPU 突然升到 95%，影响大吗？应该怎么处理？

## Business Model / Ontology instance

- 服务：`payment-service`
- Pod：`payment-service-7f8c9`
- 数据库：`payment-db`
- 上游：`checkout-service`
- 下游：`order-service`
- 业务：`在线支付`

关系：

```text
checkout-service
      ↓
payment-service
   ↙       ↘
payment-db  order-service
```

## Facts

- CPU：95%，持续 11 分钟；
- P99 延迟：180ms → 1.8s；
- 错误率：0.2% → 3.4%；
- 当前处于晚间交易高峰；
- 上一次类似事件由连接池耗尽导致。

## Rules / Methods / Boundaries

- 核心支付服务 P99 > 1s 且错误率 > 2% 持续 5 分钟，定义为 P1；
- P1 可自动扩容；
- 数据库连接池参数变更必须人工确认；
- 高峰期禁止全量重启。

## Task Context

动态组合：当前指标、依赖拓扑、交易量、最近发布、类似历史事件、服务等级、处置 SOP、当前权限。

## Evidence

Prometheus、Trace、K8s 事件、CMDB 拓扑、发布记录、历史 Incident。

## Capability

`IncidentAssessAndRecommend(service_id)`

> 当前应按 P1 处理。建议先自动扩容应用实例，同时检查数据库连接池；未经确认不要修改数据库参数或全量重启。

若权限允许，还可以进一步调用 Action Capability：

`ScaleService(service_id, replicas)`

这说明 Capability 不止是“给 AI 知识”，还可以把企业规则、权限和工具组合成可控执行能力。

# 六、场景三：投研 — 正常回调还是趋势破坏？

## 用户问题

> 科创 50 最近这次回调，是正常分歧还是趋势已经坏了？

## Business Model / Ontology instance

- 标的：`科创50ETF`
- 指数：`上证科创板50成份指数`
- 市场状态：趋势 / 分歧 / 破位
- 因子：成交量、价格结构、行业强弱、资金行为
- 策略：`中线趋势策略`

## Facts

- 从阶段高点回撤 6%；
- 仍位于中期关键趋势结构之上；
- 回调量低于上涨量；
- 核心权重未同步破位；
- 科技成长整体分化而非全面退潮。

## Rules / Methods / Boundaries

- 中线周期 4–12 周；
- 第一波回调不因短期波动直接离场；
- 缩量回调且关键结构未破，优先定义为正常分歧；
- 放量跌破关键结构且无法快速收回，升级为趋势失效。

## Task Context

价格结构、成交量、中期趋势、板块强弱、策略持仓周期、确认 / 失效条件、当前策略版本。

## Evidence

行情、成交量、行业 / 风格指数、策略规则版本、判断时间窗口。

## Capability

`TrendStateAssessment(asset, strategy)`

> 按当前中线趋势规则，这更接近正常分歧而非趋势破坏。主要依据是回调缩量且关键结构尚未破坏；若后续放量跌破并无法快速收回，则判断失效。

这个场景特别适合说明：**同样的数据，不同机构或不同策略可能得到不同结论，因为 Rule / Method 不同。**

# 七、场景四：教育 — 学生下一步应该学什么？

## 用户问题

> 王同学最近数学成绩下降，问题到底在哪里？下一步应该补什么？

## Business Model / Ontology instance

- 学生：`王同学`
- 课程：`高一数学`
- 知识点：函数、集合、不等式、指数函数
- 学习目标：`函数基础掌握`

关系：

```text
函数
 ├─依赖→ 集合
 ├─依赖→ 不等式基础
 └─前置于→ 指数函数
```

## Facts

- 最近三次函数题正确率：48%；
- 集合：92%；
- 不等式：55%；
- 错误集中在定义域和单调性；
- 课堂练习完成率正常。

## Rules / Methods / Boundaries

- 不直接根据总分推荐下一章节；
- 先检查前置知识依赖；
- 正确率低于 60% 且错误集中时优先补弱项；
- 正式学习计划由教师确认。

## Task Context

课程进度、知识点依赖、最近错误模式、学习目标、历史掌握状态、教学策略。

## Evidence

测验结果、题目-知识点映射、作业记录、课程进度、教师规则。

## Capability

`LearningGapAndNextStep(student_id)`

> 当前主要问题不是“函数整体不会”，而是不等式基础和函数定义域形成连续薄弱点。建议先补不等式与定义域，再进入单调性训练，暂不建议直接推进指数函数。

# 八、跨场景统一映射

| 概念 | 企业经营 | 运维 | 投研 | 教育 |
|---|---|---|---|---|
| Business Object | 客户 / 合同 / 项目 | 服务 / Pod / DB | 标的 / 指数 / 策略 | 学生 / 课程 / 知识点 |
| Relationship | 客户-合同-项目 | 服务依赖拓扑 | 标的-市场-策略 | 知识点依赖 |
| Fact | 逾期 18 天 | CPU 95%、P99 1.8s | 回撤 6%、缩量 | 正确率 48% |
| Rule / Method | 风险规则 | P1 / 处置规则 | 中线趋势规则 | 教学路径规则 |
| Task Context | 客户等级 + 项目状态 | 高峰期 + 拓扑 + 变更 | 周期 + 板块环境 | 课程进度 + 错误模式 |
| Evidence | ERP / CRM / 合同 | Metrics / Trace / CMDB | 行情 / 策略版本 | 测验 / 作业 / 课程 |
| Capability | 客户风险判断 | 故障判断 / 扩容 | 趋势状态判断 | 学习诊断与路径 |

四个场景不同，但逻辑一致：

> **定义业务世界 → 连接当前事实 → 按任务形成 Context → 按企业方法调用 Capability → 给出有 Evidence、有边界的判断或行动。**

# 九、对官网的使用建议

首页不要同时展示四个完整场景。建议：

1. 首屏讲：**为什么通用 AI 一进企业就不好用；**
2. 产品机制区用一个“客户风险判断”主案例，把抽象定义串成真实 instance；
3. 下方用经营 / 运维 / 投研 / 教育四个轻量场景证明同一套机制跨领域成立；
4. 技术下钻页再展示完整的 Ontology / Fact / Context / Rule / Evidence / Capability 定义。

首页尤其不要让用户先背术语。用户先看到的是：

> **原来 AI 看到的是“逾期 18 天”，Genesis 让它知道“这个 18 天在当前客户、合同、项目和公司规则下到底意味着什么，以及下一步能做什么”。**

这才是抽象概念场景化的目的。
