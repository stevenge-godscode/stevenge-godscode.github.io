# Genesis 产品概念的场景化实例

> 目的：所有抽象定义都必须能落到真实业务 instance。避免只解释 Ontology、Fact、Context、Rule、Evidence、Capability 等术语，而是用完整业务事件链让业务用户和技术负责人都能理解这些概念如何协同工作。

## 表达原则

产品介绍遵循两层表达：

1. **先说人话定义**：这个概念解决什么问题。
2. **马上给真实 instance**：在一个具体业务问题中，它到底是什么。

同一个概念至少用多个领域验证，确保不是只在某一个场景中成立。

建议固定使用以下链条：

```text
业务对象 / 关系
      ↓
当前事实
      ↓
任务上下文
      ↓
适用规则 / 方法 / 边界
      ↓
证据
      ↓
判断 / Capability / Action
```

其中：

- **Ontology / Business Model**：定义什么是什么，以及彼此什么关系。
- **Fact**：当前真实发生了什么。
- **Context**：针对当前任务，从相关对象、事实、关系、历史、规则等动态组装出的业务上下文。
- **Rule / Method / Boundary**：这家公司遇到这种情况如何判断、如何处理、什么不能做。
- **Evidence**：这个事实或判断依据什么数据、文档、事件或来源。
- **Capability**：把上述理解、规则和证据封装成可被 AI / Agent / App 重复调用的业务能力。

# 场景一：企业经营 — 哪些客户需要重点关注？

## 用户问题

> 哪些客户最近需要重点关注？为什么？

## Ontology / Business Model

具体 instance：

- 客户：`南桥集团`
- 合同：`HT-2026-0188`
- 项目：`智能供应链一期`
- 应收：`AR-2026-0912`
- 客户经理：`张经理`

关系：

```text
南桥集团
  ├─签署→ HT-2026-0188
  ├─对应→ 智能供应链一期
  └─产生→ AR-2026-0912
```

这一步回答：**这些东西分别是什么，它们彼此是什么关系？**

## Facts

当前事实：

- 合同金额：800 万；
- 应收逾期：18 天；
- 项目状态：交付中、尚未验收；
- 南桥集团为战略客户；
- 上季度曾发生一次 12 天延期回款。

这一步回答：**现在真实发生了什么？**

## Context

针对“是否需要重点关注”这个任务，Genesis 动态组装：

- 客户等级；
- 当前合同；
- 应收状态；
- 项目交付 / 验收状态；
- 历史回款行为；
- 当前责任人；
- 当前适用的经营风险规则。

注意：不是把整个 CRM / ERP 全部交给模型。

## Rules / Methods / Boundaries

这家公司的规则：

- 战略客户应收超过 15 天进入重点关注；
- 但项目尚未验收时，不直接认定为信用风险；
- 必须先检查交付与验收责任；
- 风险升级必须由业务负责人确认。

## Evidence

判断依据可以追溯到：

- ERP 应收记录；
- CRM 客户等级；
- 项目系统交付状态；
- 合同条款；
- 历史回款记录。

## AI / Capability 输出

> 南桥集团建议进入重点关注，但当前证据不足以认定为信用风险。主要原因是应收已逾期 18 天，但项目尚未完成验收。建议优先确认交付与验收责任，并由业务负责人决定是否升级风险等级。

可沉淀 Capability：

`CustomerRiskAssessment(customer_id)`

# 场景二：智能运维 — 一个告警到底严重不严重？

## 用户问题

> 支付服务 CPU 突然升到 95%，影响大吗？应该怎么处理？

## Ontology / Business Model

instance：

- 服务：`payment-service`
- Pod：`payment-service-7f8c9`
- 数据库：`payment-db`
- 上游：`checkout-service`
- 下游：`order-service`
- 业务：`在线支付`

关系：

```text
checkout-service
      ↓
payment-service
   ↙       ↘
payment-db  order-service
```

## Facts

- payment-service CPU：95%；
- 持续 11 分钟；
- P99 延迟从 180ms 升至 1.8s；
- 错误率从 0.2% 升至 3.4%；
- 当前正处于晚间交易高峰；
- 上一次类似事件由连接池耗尽导致。

## Context

针对“影响和处置”任务，动态组合：

- 当前指标；
- 服务依赖拓扑；
- 当前交易量；
- 最近发布变更；
- 类似历史事件；
- 服务等级；
- 处置 SOP。

## Rules / Methods / Boundaries

企业自己的运维规则：

- 核心支付服务 P99 > 1s 且错误率 > 2% 持续 5 分钟，定义为 P1；
- P1 可自动扩容，但数据库连接池参数变更必须人工确认；
- 高峰期禁止直接重启全部实例。

## Evidence

- Prometheus 指标；
- Trace；
- K8s 事件；
- CMDB / 服务拓扑；
- 发布记录；
- 历史 Incident。

## AI / Capability 输出

> 当前应按 P1 事件处理。payment-service 已同时出现延迟和错误率异常，并处于交易高峰。建议先自动扩容应用实例，同时检查数据库连接池；未经确认不要修改数据库参数或全量重启。

可沉淀 Capability：

`IncidentAssessAndRecommend(service_id)`

# 场景三：投研 — 这是正常回调还是趋势破坏？

## 用户问题

> 科创 50 最近这次回调，是正常分歧还是趋势已经坏了？

## Ontology / Business Model

instance：

- 标的：`科创50ETF`
- 指数：`上证科创板50成份指数`
- 市场状态：趋势 / 分歧 / 破位
- 因子：成交量、价格结构、行业强弱、资金行为
- 策略：`中线趋势策略`

## Facts

例如当前观察：

- 指数从阶段高点回撤 6%；
- 仍位于中期关键均线之上；
- 回调成交量低于前期上涨成交量；
- 核心权重未出现同步破位；
- 科技成长板块整体处于分化而非全面退潮。

## Context

当前任务需要组合：

- 当前价格结构；
- 成交量；
- 中期趋势；
- 板块强弱；
- 策略持仓周期；
- 用户定义的确认 / 失效条件。

## Rules / Methods / Boundaries

企业 / 策略自己的判断方法：

- 中线周期 4–12 周；
- 第一波回调不因短期波动直接离场；
- 缩量回调且关键趋势位未破，优先定义为正常分歧；
- 关键趋势位放量破坏并无法快速收回，才升级为趋势失效。

这里强调：相同市场数据，不同机构或策略体系可能得到不同判断，因为**工作方法不同**。

## Evidence

- 行情数据；
- 成交量；
- 行业 / 风格指数；
- 策略规则版本；
- 判断所引用的具体时间窗口。

## AI / Capability 输出

> 按当前中线趋势规则，这更接近正常分歧而非趋势破坏。主要依据是回调缩量且中期关键结构尚未破坏。若后续出现放量跌破关键趋势位且无法快速收回，则判断失效。

可沉淀 Capability：

`TrendStateAssessment(asset, strategy)`

# 场景四：教育 — 学生下一步应该学什么？

## 用户问题

> 王同学最近数学成绩下降，问题到底在哪里？下一步应该补什么？

## Ontology / Business Model

instance：

- 学生：`王同学`
- 课程：`高一数学`
- 知识点：函数、集合、不等式、指数函数
- 题目：`Quiz-2026-091`
- 学习目标：`函数基础掌握`

关系：

```text
函数
 ├─依赖→ 集合
 ├─依赖→ 不等式基础
 └─前置于→ 指数函数
```

## Facts

- 最近三次测验函数题正确率：48%；
- 集合：92%；
- 不等式：55%；
- 主要错误集中在定义域和单调性判断；
- 课堂练习完成率正常。

## Context

任务上下文包括：

- 当前课程进度；
- 知识点依赖；
- 最近错误模式；
- 学习目标；
- 学生历史掌握状态；
- 学校的教学策略。

## Rules / Methods / Boundaries

学校 / 教师的教学方法：

- 不直接根据总分推荐下一章节；
- 先检查前置知识依赖；
- 正确率低于 60% 且错误集中时优先补弱项；
- 学习建议由教师确认后进入正式学习计划。

## Evidence

- 测验结果；
- 题目知识点映射；
- 作业记录；
- 课程进度；
- 教师规则。

## AI / Capability 输出

> 当前主要问题不是“函数整体不会”，而是不等式基础和函数定义域判断形成了连续薄弱点。建议先补不等式与定义域，再进入单调性训练；暂不建议直接推进指数函数。

可沉淀 Capability：

`LearningGapAndNextStep(student_id)`

# 跨场景统一定义

四个场景虽然业务完全不同，但底层结构一致：

| 概念 | 企业经营 | 运维 | 投研 | 教育 |
|---|---|---|---|---|
| Business Object | 客户 / 合同 / 项目 | 服务 / Pod / DB | 标的 / 指数 / 策略 | 学生 / 课程 / 知识点 |
| Relationship | 客户-合同-项目 | 服务依赖拓扑 | 标的-市场-策略 | 知识点依赖 |
| Fact | 逾期 18 天 | CPU 95%、P99 1.8s | 回撤 6%、缩量 | 正确率 48% |
| Context | 客户等级 + 项目状态 | 高峰期 + 拓扑 + 变更 | 趋势周期 + 板块环境 | 课程进度 + 错误模式 |
| Rule / Method | 风险判断规则 | P1 / 自动扩容规则 | 中线趋势规则 | 教学路径规则 |
| Evidence | ERP / CRM / 合同 | Metrics / Trace / CMDB | 行情 / 策略规则 | 测验 / 作业 / 课程 |
| Capability | 客户风险判断 | 故障判断与处置 | 趋势状态判断 | 学习诊断与路径 |

这张表的目的不是给首页展示，而是用于验证 Genesis 的核心概念是否真正跨领域成立。

# 对官网的建议

首页不要同时展示四个完整案例。建议采用：

1. 首屏只讲主逻辑：**通用 AI 的痛点 → Genesis → 企业专属 AI 的价值**；
2. “Genesis 怎么做到”区域选择 **一个最容易理解的主案例**，把抽象定义转成 instance；
3. 用户继续下滑时，再用 3–4 个领域卡片证明同一机制可以进入不同业务世界；
4. 技术下钻页再展示完整的跨场景概念映射。

推荐主案例优先级：

1. **企业经营 / 客户风险**：最通用，业务负责人容易理解；
2. **智能运维**：最适合技术负责人验证机制；
3. 投研：体现“同样数据 + 不同方法 → 不同判断”，非常适合解释 Domain Pack；
4. 教育：证明架构并非只适用于经营 / IT 场景。

# N04 场景化验收要求

N04 后续定稿时，所有核心定义必须至少满足：

- 有一句非技术定义；
- 有一个具体 instance；
- 能在至少 3 个完全不同的业务领域复用同一结构；
- 能把 `Object → Fact → Context → Rule → Evidence → Capability` 串成完整链条；
- 场景中的规则必须体现“企业自己的做法”，而不是只有行业通用知识；
- 场景中的 Context 必须是针对当前任务动态组合，而不是静态大 Prompt。
