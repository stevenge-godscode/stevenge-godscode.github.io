# Genesis 端到端闭环场景框架

> 目标：任何 Genesis 场景都不能只停留在“理解 / 判断”。一个完整场景必须把企业真实业务从感知事实、理解语义、形成判断、采取行动、验证结果到沉淀能力串成闭环，并且每一阶段都能落到具体业务 instance。

---

# 1. Genesis 的完整闭环

对业务用户统一使用六个动作：

> **看见 → 看懂 → 判断 → 行动 → 验证 → 沉淀**

技术对应：

```text
Observe / Sense
      ↓
Understand / Contextualize
      ↓
Decide / Judge
      ↓
Act / Execute
      ↓
Verify / Observe Outcome
      ↓
Improve / Evolve
      ↺
New Facts
```

核心定义：

> **理解和判断改变“认知”；Action 改变真实业务状态；Verify 确认是否真的改变；Improve 把结果和经验沉淀成下一轮可复用能力。**

---

# 2. 六个阶段分别回答什么

## S1 — 看见 / Observe

回答：

> **真实世界现在发生了什么？**

具体包括：

- 数据；
- 事件；
- 状态；
- 时间；
- 来源；
- 变化。

不是“模型读到了一段文字”，而是形成可追溯 Facts。

## S2 — 看懂 / Understand

回答：

> **这些事实在当前业务里意味着什么？**

具体包括：

- Business Object；
- Relationship；
- Semantic；
- History；
- Task Context；
- 当前用户 / 角色。

这是从 Data 到 Business Meaning 的转换。

## S3 — 判断 / Decide

回答：

> **按这家企业自己的方法，现在应该怎么看这件事？**

结合：

- Rules；
- Methods；
- Evidence；
- Uncertainty；
- Permission / Boundary。

输出不是一定要“yes / no”，也可以是：

- 分类；
- 风险级别；
- 优先级；
- 建议；
- 不确定；
- Abstain / 请求人工判断。

## S4 — 行动 / Act

回答：

> **基于当前判断，允许改变真实业务世界的什么状态？**

Action 可以是：

- Create / Assign Task；
- Trigger Workflow；
- Send Request；
- Update Status；
- Call API；
- Scale Service；
- Generate Work Product；
- Schedule Monitoring；
- Escalate for Approval。

Action 必须受 Capability、权限、Rule、风险等级和人工审批约束。

> **能判断 ≠ 能执行。**

## S5 — 验证 / Verify

回答：

> **行动之后，业务真的变好了吗？目标状态发生了吗？**

必须重新观察：

- 新状态；
- 结果指标；
- 是否执行成功；
- 是否达到预期；
- 是否产生副作用；
- 是否需要回滚 / 升级。

因此 Action 之后不能直接宣布任务完成。

## S6 — 沉淀 / Improve

回答：

> **这次工作产生的经验，下一次如何更好地复用？**

可以沉淀：

- 新 Facts / History；
- Decision Trace；
- Outcome；
- Capability Usage；
- Evidence Pattern；
- Context Template；
- Approved Rule / Method Update；
- Domain Pack 更新；
- 专家反馈。

注意：

> **Improve 不等于让 LLM 自动改规则。**

规则、方法、权限和关键 Capability 的变化仍需企业治理、版本管理和必要人工确认。

# 3. 闭环完整度与 Proof Level 必须分开

## Proof Level

仍使用：P0 → P1 → P2 → P3 → P4。

它回答：

> **这个场景的真实性 / 证据成熟度到哪一级？**

## Loop Coverage

新增六阶段覆盖：

| Code | 阶段 | 必须有具体 instance |
|---|---|---|
| `S1` | Observe / 看见 | 当前事实与来源 |
| `S2` | Understand / 看懂 | 对象、关系、上下文 |
| `S3` | Decide / 判断 | 规则、方法、Evidence、结论 |
| `S4` | Act / 行动 | 实际动作、目标系统、权限 |
| `S5` | Verify / 验证 | 行动后的新状态与成功标准 |
| `S6` | Improve / 沉淀 | 反馈、Trace、能力 / 规则改进方式 |

一个场景可以：

```text
Proof = P2
Loop Coverage = S1–S3
```

含义：真实客户 POC 已验证认知 / 判断，但还没有动作闭环。

只有：

```text
Loop Coverage = S1–S6
```

才允许称：

> **端到端闭环场景 / End-to-end Closed-loop Scenario**

# 4. 场景一：企业经营 — 客户风险与跟进闭环

## 用户问题

> **这个客户现在有风险吗？需要做什么？**

### S1 看见

实际 instance：

- 客户：南桥集团；
- 应收：逾期 18 天；
- 合同：800 万；
- 项目：交付中、尚未验收；
- 来源：ERP、CRM、项目系统、合同。

### S2 看懂

Genesis 识别：

- 南桥集团是战略客户；
- 应收对应合同和当前项目；
- 付款条件与项目验收有关；
- 历史上有一次延期回款。

### S3 判断

企业规则：

- 战略客户逾期 15 天进入重点关注；
- 项目尚未验收时不得直接认定信用风险；
- 正式信用等级调整需要人工确认。

判断：

> **进入重点关注，但证据不足以认定信用风险。**

### S4 行动

允许执行：

1. 在 CRM 创建“重点关注”跟进任务；
2. 分配给客户经理；
3. 向项目负责人发起“确认验收状态”请求；
4. 拉取合同付款条件进入复核；
5. 发起风险复核 Workflow。

禁止自动：

- 修改正式信用等级；
- 发违约通知；
- 冻结客户。

### S5 验证

重新读取业务状态：

- 跟进任务是否创建成功；
- 客户经理是否接收；
- 项目负责人是否补充验收信息；
- 风险复核是否进入正确流程；
- 新 Evidence 是否改变原判断。

例如后续发现：

> 项目实际已完成交付，但客户侧验收流程未结束。

这个信息成为新的 Fact，风险判断重新计算。

### S6 沉淀

保留：

- 本次 Decision Trace；
- 用过的 Facts / Rules；
- Action / Approval；
- 最终 Outcome；
- 专家是否覆盖 AI 判断。

如果类似案例多次出现，可由业务负责人评审是否把“客户侧验收延迟”增加为风险判断中的正式 Context / Rule，而不是模型自己修改规则。

# 5. 场景二：智能运维 — 故障判断与恢复闭环

## 用户问题

> **支付服务异常严重吗？应该怎么处理？**

### S1 看见

- `payment-service` CPU 95%；
- P99 1.8s；
- Error Rate 3.4%；
- 当前交易高峰；
- 来源：Prometheus、Trace、K8s Event。

### S2 看懂

- payment-service 属于核心支付链路；
- 上游 checkout，下游 order / DB；
- 最近发生版本发布；
- 历史类似事件曾由连接池耗尽导致。

### S3 判断

企业规则：

- P99 > 1s + Error Rate > 2% 持续 5 分钟 → P1；
- 高峰期禁止全量重启；
- 自动扩容允许，DB 参数变更需人工确认。

判断：

> **P1 事件，优先扩容并检查数据库连接池。**

### S4 行动

- 自动扩容应用实例；
- 创建 Incident；
- 通知值班负责人；
- 自动抓取连接池 / Trace Evidence；
- 禁止自动全量重启；
- DB 参数调整进入人工审批。

### S5 验证

行动后持续观察：

- CPU；
- P99；
- Error Rate；
- 交易成功率；
- 新实例健康；
- 是否达到恢复阈值。

若扩容后指标未恢复，则触发下一诊断步骤，而不是宣布故障已解决。

### S6 沉淀

- Incident Timeline；
- 根因；
- 哪个 Action 有效；
- 哪些 Evidence 最有区分度；
- 人工修改过哪些建议；
- 经审批更新 Runbook / Capability。

# 6. 场景三：投研 — 趋势判断与持续跟踪闭环

## 用户问题

> **这次回调是正常分歧还是趋势破坏？下一步怎么办？**

### S1 看见

- 当前价格；
- 回撤幅度；
- 成交量；
- 板块强弱；
- 风格指标；
- 来源：行情 / 市场数据。

### S2 看懂

- 当前处于中线持仓周期；
- 回调发生在什么趋势结构里；
- 当前策略属于哪套方法；
- 相关板块是分化还是系统性退潮。

### S3 判断

按照企业 / 策略自己的规则：

> 当前更接近正常分歧；若放量跌破关键结构且无法快速收回，则判断失效。

### S4 行动

这里 Action 不必等于自动交易。

可以受控执行：

- 创建观察项；
- 记录判断与失效条件；
- 设置监控规则；
- 触发关键条件提醒；
- 更新研究 / 持仓观察报告；
- 高风险交易 Action 继续由另外授权 Capability / 人工执行。

### S5 验证

后续行情触发条件时：

- 是否保持关键趋势位；
- 成交量结构是否改变；
- 判断条件是否失效；
- 当前结论是否需要更新。

### S6 沉淀

- 保存当时的市场 Context；
- 判断依据；
- 后续 Outcome；
- 策略是否被人工调整；
- 哪类判断在什么市场状态下更有效。

策略 Rule 的正式修改仍需策略负责人确认。

# 7. 场景四：教育 — 学习诊断到教学反馈闭环

## 用户问题

> **学生哪里没掌握，下一步应该学什么？**

### S1 看见

- 三次测验函数题正确率 48%；
- 集合 92%；
- 不等式 55%；
- 作业 / 课堂练习记录。

### S2 看懂

- 函数依赖集合和不等式基础；
- 错误集中在定义域和单调性；
- 当前课程进度和教学目标。

### S3 判断

> 问题不是“函数整体不会”，而是前置不等式基础 + 定义域连续薄弱。

### S4 行动

- 生成补弱学习任务；
- 分配不等式 / 定义域练习；
- 把学习路径建议发送教师确认；
- 暂缓进入指数函数；
- 教师批准后进入正式学习计划。

### S5 验证

下一轮学习 / 测验后重新观察：

- 弱项正确率；
- 错误类型；
- 学习完成度；
- 是否达到进入下一知识点的标准。

### S6 沉淀

- 更新学生 Mastery State；
- 保存推荐路径与结果；
- 教师修改记录成为反馈；
- 可用于改进教学 Capability / Context Template，但正式教学规则由教师 / 教研治理。

# 8. 首页如何表达闭环

首页不需要同时完整展开四个场景。

推荐：

## 主场景

用一个完整经营 instance 串完：

> **看见 → 看懂 → 判断 → 行动 → 验证 → 新事实**

让用户真正理解“AI 为公司工作”的闭环。

## 跨场景证明

后面用一张紧凑矩阵展示：

| 场景 | 看见 | 看懂 | 判断 | 行动 | 验证 / 反馈 |
|---|---|---|---|---|---|
| 经营 | 应收 / 项目 | 客户 / 合同关系 | 风险判断 | 跟进 / 复核 | 回款 / 验收新状态 |
| 运维 | Metrics / Trace | 拓扑 / 变更 | P1 / 根因 | 扩容 / Incident | 指标是否恢复 |
| 投研 | 行情 / 成交量 | 趋势 / 策略 Context | 分歧 / 破坏 | 观察 / 提醒 / 报告 | 条件是否失效 |
| 教育 | 测验 / 作业 | 知识依赖 | 薄弱点诊断 | 学习任务 | 下一轮掌握度 |

这样证明：

> **Genesis 不是只会在一个案例里完成“理解”，而是同一套闭环结构可以进入多个真实业务世界。**

# 9. Proof Registry 的新要求

以后每个 Scenario Registry 条目必须增加：

- `Loop Coverage`：S1–S6；
- `Action Target`：哪个真实系统 / Workflow / API 被改变；
- `Verification Signal`：什么新 Fact 证明 Action 是否有效；
- `Feedback Asset`：什么被沉淀；
- `Human Governance`：哪一步必须人工确认。

首页只把符合当前真实成熟度的阶段画成“已验证”；尚未实现的阶段必须标为“设计闭环 / 下一步验证”，不能用视觉暗示全部已经生产可用。

# 10. 最终产品哲学

Genesis 的终点不是：

> **回答一个问题。**

也不只是：

> **做出一个判断。**

而是：

> **理解真实业务，在企业规则和边界内采取行动，观察行动后的世界，并把结果沉淀成下一次可复用的业务能力。**

最短闭环表达：

> **看见真实业务，理解业务含义，做出可靠判断，采取受控行动，用结果继续改进。**
